# UI 断言规则

本技能只维护断言能力，不定义录制、执行或审批步骤。`qa-ui-record` 写断言、`qa-ui-basic` 排查失败、测试数据视图编辑断言时加载；普通录制不涉及断言设计时不单独加载。

## 1. 来源

- 每个 expect 对应 caseDocument 中一条「预期 + 来源」。
- 来源优先级：用户需求/用例说明 → 页面规则（页面既有基线）→ 已声明基线。
- 默认来源写「页面规则」；不写「页面显示」「实际值」「看页面」。
- 页面规则与常识冲突时记录待确认，不用实际结果倒推预期。

## 2. 业务断言与守卫断言

- 每个 case 至少一条 business 断言，断言业务结果：记录出现、状态变更、详情字段等于输入、错误提示出现且数据未写入。
- guard 只用于导航/前置校验（页面打开、角色可见、无报错），不能替代业务结果。
- 一个 expect 只断言一个事实，失败信息要能定位到业务步骤。

## 3. 数据不变量

列表和筛选断言优先断言不变量，不绑定录制当天的数据量：

- 不要硬编码「共 N 条」或固定行数；测试数据会增长。
- 筛选后：总数大于 0、总数等于当前行数、每一行都满足筛选条件。
- 重置后：总数等于筛选前捕获的总数，行数等于 `min(总数, 每页条数)`。
- 精确条数只在唯一键/隔离数据时使用，例如按唯一合同编号或唯一名称查询。
- 日期/状态范围：每一行都落在范围内，而非只检查第一行。
- 读取用唯一业务编号/名称定位，不用第一行、最新一条或总数推断目标记录。
- 动态值断言格式或正则，不断言具体时间、随机 ID、自增序号。

## 4. 写法

- 用 web-first 断言：`toBeVisible`、`toHaveText`、`toHaveCount`、`toHaveValue`、`toHaveURL`；不用 `expect(await ...)`。
- 不只断言 loading、骨架屏、样式类、请求码等中间态；等业务信号。
- 日志里的 assert 行可能截断可访问名；最终断言用输入/计划中的完整业务值，不照抄前缀。
- 断言定位器与操作共用业务定位器，不用录制 ref、自动 id、body 全文匹配。
- 不使用 `waitForTimeout`、固定 sleep、轮询；必须等待时用 web-first 超时并说明业务原因。
- 不用 try/catch 吞掉断言失败后继续。

## 5. 录制时的断言验证

- 每个业务步骤后立即用 `browser_verify_*` 验证，再继续下一步。
- `generator_read_log` 核对动作与断言都已入日志；日志没有的业务预期先现场验证，验证不了就写明原因，不写成通过。
- 只把日志中有证据的断言写进 spec；未验证的预期不写。
- 断言失败先查数据、角色权限、前置状态和操作步骤，不先改预期。

## 6. 断言编辑与同步

修改断言时同时更新：

1. spec 中的 expect；
2. `.asset.json` 的 `caseMeta.cases[].assertions`；
3. `.md` 的 `qa-ui-case` 元数据块和「用例与断言」表；
4. spec 的 `sha256`，并按工作流重新 finalize / 准备回放。

只改展示元数据不改 spec 会造成“文档通过、执行仍旧”的假象；只改 spec 不改资产会被哈希校验拒绝。

## 7. 失败判定：录制问题还是断言问题

| 证据 | 判定 |
| --- | --- |
| 操作后页面状态正确，Expected/Received 只差数据量、文案或动态值 | 断言问题：改为不变量/正则 |
| 页面没出现预期行、筛选条件未生效、请求缺少参数 | 录制或产品问题：查步骤、定位器、请求；不要放宽断言掩盖 |
| 选择/点击/输入没执行，或定位到错误控件 | 录制问题：重录该步骤 |
| 断言依赖第一行/固定总数，数据增长后失败 | 断言问题：改为全量不变量 |
| 断言通过但业务结果错误 | 断言覆盖不足：补业务结果断言，不删断言 |

排查时先读完整错误、失败截图/error-context 和请求；不要为了通过直接删断言或改小范围。

## 8. 自检

- 每条断言有来源，且来源不是“页面显示”。
- 至少一条业务断言，guard 不替代业务结果。
- 列表/筛选没有硬编码总数；每行都验证筛选条件。
- 动态值用格式/正则，完整业务值不截断。
- 断言使用业务定位器，无 ref、自动 id、样式类例外。
- spec、资产元数据、说明表三者一致，哈希已更新。
- 失败信息能定位业务步骤；未验证的预期没有写成通过。

## 禁止

- 不用实际值倒推预期，不为通过删断言、跳过测试或放宽到无业务含义。
- 不把产品缺陷写成“预期如此”来让用例通过。
- 不把账号密码、真实个人信息或生产敏感数据写进断言、说明或日志。
