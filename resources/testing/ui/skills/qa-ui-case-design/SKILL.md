# UI 用例生成规则

本技能维护用例设计规则。只要求设计或检查粒度时不启动浏览器；需要探索和生成可执行候选时转 qa-ui-basic，按其探索顺序与工具契约执行。自由发现可补充原清单之外的功能，不自动扩大正式用例或执行权限。

## 覆盖与来源

生成前按用户指定范围建立覆盖清单，包含检查项编号、功能、输入条件、预期及来源、计划 caseId。已有设计稿逐项映射，不直接当成可执行脚本；遗漏、受阻和待确认项保留原因，不从清单删除。按范围内风险决定先后顺序，用一句话说明先测这一批的理由。

实际探索或生成时，将这份覆盖清单按 qa-ui-basic 的 [本轮清单规程](../qa-ui-basic/references/coverage.md)登记为稳定功能与独立检查项，不再维护另一套编号。只有实际保存成功的准确候选版本及业务预期引用才进入生成统计；已设计但不能自动执行的审批项保留说明与受阻原因。纯需求设计不为统计启动探索或制造可执行候选。

结合需求与实际页面盘点功能，包括展开区、行内操作和相关详情/表单入口。探索任务按 qa-ui-basic 引用的探索提示词先处理指定功能，再继续自由发现；新发现单独入队并记录来源，不受初始功能清单限制，也不自动扩大正式用例执行或写入授权。未提供的能力不凭常见页面经验补造；需求要求但页面缺失的能力保留为缺口。旧设计稿或历史录制中的列数、选项、状态名称和数据量须核对当前目标，不能直接移用。

每条用例具备来源、前置条件、操作或输入、可判定预期，追溯到需求、风险或覆盖清单中的检查项。预期依据用户要求、明确页面规则或已确认基线，保留可定位引用；不以运行实际结果或模型猜测倒推预期。缺少会改变预期的业务口径时标为待确认，不猜造正确结果。

现场观察只证明现状，不自动成为已确认基线；推测、待确认口径和缺陷现状不能包装为 rule/baseline。已知缺陷仍按有依据的正确行为设计，实际错误另记，不设计“筛选不生效即通过”的回归用例。预期优先描述用户可见的业务结果；无明确接口契约时，不把请求参数名、请求次数或 blob/iframe 等实现机制设为业务正确性的必要条件，这些可作为诊断证据。

## 按功能选择检查点

仅对本次范围内适用的检查项设计，不机械展开所有选项和组合；同一规则的等价输入选代表值，不同业务分支、边界或预期分别覆盖。缺规则列待确认，缺数据列执行受阻，不用减少断言掩盖缺口。

| 功能 | 设计时要核对的判定条件 |
| --- | --- |
| 查询与筛选 | 按规则选择命中、无结果、组合条件或重置场景。命中例须有已确认的目标记录；验证排除能力须有不符合条件的对照记录，避免原本全量就符合条件。组合条件的数据应能区分交集与只生效一个条件；无结果例须有依据确认无匹配数据，不能只用循环遍历零行来判通过 |
| 日期、数值与表单输入 | 依据已定义的范围、精度、必填及字段联动选择有效、无效和边界条件；验证某条规则时，其余输入满足必要前提。日期区间检查实际区间，不用“同一年”替代；必填标记存在不代表提交校验已覆盖 |
| 分页与每页容量 | 数据量须足以区分页码或容量是否生效，并核对目标页记录。仅 3 条数据时切到 20 条/页并断言行数不超过 20，不能证明容量切换有效；数据不足时区分控件回显/禁用态检查与尚受阻的跨页取数检查 |
| 详情与统计 | 详情绑定唯一业务对象，多个必要字段的一致性可共同证明一个目标。统计数值须有已确认的状态、时间、单位和数据范围口径；当前页行数不代表全部数据，不自行推导“总数减草稿”等公式 |
| 角色与权限 | 使用存在且处于目标状态的记录，核对当前角色与处理人/数据归属关系。非法 id 的错误处理、非处理人入口限制与处理人可操作分别设计；无按钮、空待办或请求带 assignee 均不能单独证明完整权限隔离或后端拒绝越权 |

## 审批用例关联

用户范围涉及提交审批、审批节点、处理人、审批权限、可选分支或审批终态时，先加载实际测试工作区中已登记的 qa-approval-workflow，再生成对应审批 case；不能只生成列表、查询或表单入口 case 后把审批范围略去。探索中新增审批线索的条件加载按 qa-ui-basic 引用的探索提示词执行；自由发现默认仍只探索，只有属于本次设计范围时才生成审批 case。普通功能不预加载审批正文。该技能是项目资源，通常位于实际工作区 `.pi/skills/qa-approval-workflow/SKILL.md`，不使用客户端仓库的固定绝对路径。未登记或缺少参考文件时报告缺失，审批项保留为待确认，继续不依赖它的设计，不猜审批链或静默套用其他流程。

按该技能选择本次业务的准确流程模型与发起部门，读取对应完整链、人员基线及核实范围；用户本次提供的对照表优先。覆盖清单增加流程模型、发起部门、节点序号/角色、动作或分支、预期状态/下一处理人、来源与核实状态，并为范围内的独立检查项分配 caseId。角色名不等于登录账号；缺失人员、开关或未核实流程分别标为待确认，不借用历史案例补齐。

| 范围内的审批检查项 | 对应 case 设计 |
| --- | --- |
| 提交及节点流转 | 提交后进入首个节点；各节点已定义动作后的下一节点、处理人和状态，分别成例 |
| 审批角色与权限 | 当前处理人可见并可用的动作；非当前处理人的访问或操作限制，依据已确认权限规则分别成例 |
| 可选节点与流程分支 | 有来源的启用、跳过及路由条件分别成例；拒绝、退回、撤回仅在需求或配置已定义且属于本次范围时生成 |
| 节点专属材料与操作 | 对应流程要求的定稿、终稿、盖章、确认或归档各自成例；有规则依据的缺失材料校验另成例，不把合同特例套到采购或立项 |
| 终态 | 对应流程的列表/详情完成状态、实际启用节点记录及必要附件或归档结果，不以到达最后节点代替终态断言 |

按用户范围和实际流程推导数量，不默认展开全部模型、部门或不存在的分支。同人连续出现仍按节点序号分别追溯。每例独立准备处于目标节点的专属记录及角色身份，不依赖前一条审批 case 留下状态；无法准备时标为执行受阻。仅明确要求的完整审批链另列 E2E。

只要求设计时生成上述用例说明与覆盖映射，不创建业务记录、不提交或审批。缺执行能力不等于缺设计范围：多角色审批目前不能交给 qa-ui-basic 自动执行，保留已设计用例并说明受阻，不伪造成功轨迹、候选或通过结果；实际执行仍须满足 qa-approval-workflow 的能力和授权边界。

## 单目标粒度

一条 case 只验证一个独立业务目标及一种输入条件组合；组合可以包含多个字段，不等于只能操作一个字段。一个 Playwright test、一个页面或一次探索不天然等于一个独立业务目标；不把断言数当作用例数。

| 合并场景 | 拆分方式 |
| --- | --- |
| 合同编号命中、无结果、重置 | 编号命中；编号无结果；带编号筛选后重置 |
| 合同名称命中、无结果、重置 | 名称命中；名称无结果；带名称筛选后重置 |
| 表头、统计卡和发起入口 | 列表表头结构；统计卡标签与单位；发起入口可达 |
| 上一页、下一页、查询后页码恢复 | 上一页；下一页；查询后的页码行为 |
| 草稿命中、部门负责人审核命中、法务审核无结果 | 三种条件各自成例，不在一个 test 内依次验证，避免前一条件失败使后续条件未执行 |

同一目标可以有多个必要断言。例如无结果查询同时检查总数为零、无数据行和空态；组合筛选验证条件交集也是一个目标。打开新建表单后检查必要字段与操作入口可以共同证明表单可达，不表示提交和必填校验已覆盖。只有用户明确要求端到端流程时才保留跨功能链，在标题与覆盖清单标为 E2E，不替代各功能独立用例。

必要的初态校验可以保留；但另一种输入的完整查询结果验证不是本例的初态准备。独立参数场景即使用参数化组织，也各自对应 caseId、初态和执行结果，不以循环、软断言或累计断言数代替拆分。

## 独立执行

每例自行准备并核对身份、初态和数据，必须能单独运行、调换顺序，不依赖另一例的结果、残留业务数据、筛选、页码或浏览器状态。可使用共用登录准备，但业务初态仍由本例建立。登录、导航、必要数据准备和清理不增加业务测试目标；例如重置例先建立筛选状态，不附带验证命中和无结果两个目标。

固定记录和精确数量须有可重复核对的基线；数据漂移时报告前置不满足，不随当前结果改写预期。只检查“结果均符合条件”不能证明没有漏掉应命中的记录，须按本例目标核对已知应命中对象，或有依据的完整结果集合。

写操作的数据隔离、唯一标识和清理按 qa-ui-basic 及实际授权执行；本技能不授予写入权限。空表单或无效输入点击“提交”仍属于潜在写操作，不能因历史上未发请求、预期被校验拦截或提交后总数未变就归为只读。

## 探索与候选衔接

生成可执行候选时，一次探索任务只对应一个独立用例目标和一种输入条件，在探索前冻结 expected。qa_ui_save_candidate 要求 case.expected 完整等于 task.contract.expected，每条预期都有业务断言。

发现已冻结任务混合多个目标时，保留原任务，回到覆盖清单拆分目标并分别取得真实探索证据；不删冻结预期、伪造轨迹、复制同一混合脚本改名凑数或改写已冻结版本。工具故障仍遵守原流程的停止与恢复规则，不把重新设计当成绕过故障的理由。

## 数量与交付检查

数量由独立覆盖项推导，不固定条数，不为凑数添加无来源场景。探索动作预算不决定用例数量。

复用历史资产时先核对业务检查项、版本关系及执行记录；修订版不重复计新增覆盖。文档中的计划条目、实际脚本和执行结果逐项对齐，缺失条目保留未生成/未执行及原因；结果只能证明对应脚本版本，前一条件失败后未到达的检查不能记为已执行。

交付前逐项核对单目标、独立初态与数据、预期来源和覆盖映射。分别记录已设计、已生成候选、已验证、已发布、受阻或待确认阶段及实际执行结果；候选不等于正式资产，受阻不计为已生成或通过。只完成部分范围时明确说明，不宣称整个页面或全部设计条目已完成。

最后反查范围内功能、业务分支与有依据的边界是否都有去向，是否遗漏因数据、身份或自动化能力受阻的设计；再问“功能完全不生效时，这组数据和预期是否仍会通过”，若会，补有区分力的数据或收窄该例的覆盖声明。缺陷结论不得超过实际断言范围，旁路观察和待确认项另列。

静态保存和成功回放不能自动证明业务粒度或语义覆盖完整；这些仍须按本技能核对。失败、未执行与待确认项不得因其他用例通过而抹除。

本轮汇总引用清单工具实际返回的准确版本，同时核对已有候选的功能与全部应生成检查项的缺口；一条候选不能代表该功能全部场景完成。统计公式、历史复用和零分母处理以本轮清单规程为准，不手工另设口径。
