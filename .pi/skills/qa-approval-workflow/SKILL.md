# 多角色审批流执行

> 按需加载：需要执行/验证多角色审批流，或录制任务需要覆盖审批入口、审批状态与逐节点操作时加载。只覆盖入口/状态时可在 `qa-ui-record` 内完成，不必加载本技能；但普通页面录制不能因此跳过审批入口。
>
> 本技能是多角色审批执行规程，不替代 `qa-ui-record` 的入口盘点和 case 生成；加载它也不会自动生成用例。
>
> 安装位置：本文件必须位于实际测试工作区的 `.pi/skills/qa-approval-workflow/SKILL.md`；只放在应用仓库不会对其他工作区生效。

## 适用与前置

测试环境以用户原话、项目配置或当前应用权限模式为准；应用权限为“完全权限”时视为已授权本次任务。业务层不再逐项询问审批操作，但“每次确认”模式下工具调用仍由应用逐次弹窗，拒绝时按未授权处理，不得绕过；生产/真实业务数据仍需明确授权。
需要：记录名称或 id、详情页路由、各节点处理人账号。账号从「系统管理 → 用户管理」读取，统一测试密码由宿主提供；不向用户索要账号、密码或逐个部门账号，不写入脚本、日志或报告。
当前 `qa_ui_login` 的 auto 只使用项目配置中的账号；多角色场景需用 start/complete 逐个保存私有登录态，或拆分为多个批次，并用显式 loginId 传给 `qa_ui_prepare`。若当前工具不能在一次准备中提供多个登录态，停止并报告限制，不要改写脚本或把凭据明文写入。

## 与当前 UI 测试工作流的边界

- 本技能负责多角色审批执行，不负责生成 case；审批入口、权限、状态和校验 case 由 `qa-ui-record` 覆盖。
- 逐节点操作使用当前登记的官方浏览器工具并保留页面证据；不要用直接调接口改状态替代页面操作，除非任务明确允许。
- 多角色登录态不是无限可并行的；按上面的单账号/显式 loginId 限制拆分批次，不能把多个账号密码写进同一脚本。

## 1. 登录与租户

- `/login` 只有用户名、密码两个输入框；提交后若进入 `/tenant/switch`，选「项目管理」并点「立即选择」。
- 每个账号使用独立 browser context，避免串号；临时 storageState 权限 0600，结束删除。
- 处理人姓名映射 username：用户管理页，或带 `x-client-code` 请求头请求 `/api/base-service/user/page?pageNum=1&pageSize=100`。列表可能分页或缺行；找不到时按拼音尝试并验证登录，不要猜密码。

## 2. 审批人解析（审批流配置）

审批链不是页面手填，而是由「流程模型 + 发起部门」从审批流配置实时解析：

- 业务类型对应流程模型，例如经营合同 = **项目立项已签合同审批流**（modelKey `ProjInitiationSignedContractProcessModelKey`）。
- 进入 **流程表单 → 审批流配置**，选择模型；表格按发起部门列出 **部门负责人、部门分管领导、总经理、董事长**。
- 其余节点（法务、合同管理员、经营发展部、市场营销部、发起人上传定稿、合同管理员盖章、发起人确认）由流程模型固定，不随部门变化。
- 配置页提示：审批人按岗位、部门和流程审批人角色实时查询，需在用户管理中维护对应关系。
- 接口：`/api/project-management-backend/v1/web/process-mgt/flow-config/models` 与 `.../flow-config/approver-matrix?modelKey=<modelKey>`。

解析顺序：

1. 确认本次业务模型和发起部门。
2. 读配置矩阵得到部门相关审批人，叠加固定节点，得到完整期望链。
3. 把姓名映射到账号，准备逐个登录。
4. 创建后以详情页实际节点为准；与期望链不一致时记录配置或任务生成问题。

经营合同 + 软件事业部示例（2026-11-04 实测）：

辛晓岩（部门负责人）→ 科技公司法务 → 刘波（合同管理员）→ 潘琴荣、朱栋华（经营发展部）→ 许玲懿（市场营销部）→ 费定（部门分管领导）→ 陈振飞（总经理）→ 叶圣炯（董事长）→ pms_admin（发起人上传定稿）→ 刘波（合同管理员盖章）→ pms_admin（发起人确认）。

创建页选择部门后审批人字段可能保持禁用，这是页面显示问题；后端仍按配置生成审批链，不要据此判断没有审批人，也不要在字段里手填。

## 3. 起点

- 创建并提交记录，捕获 initiate 响应里的 id；合同编号可能由后端自动生成（本次为 `HSKJ-JYHT-2026-004`）。
- 打开详情页 `.../OperationContractDetail?id=<id>` 读取当前「流程节点 / 处理人」。
- 不要用 `BusinessProcess?kind=...&id=...` 预览页判断权限：该页只读，可能没有审批按钮。

## 4. 逐节点审批（循环到终态）

1. 读详情页审批流程尾部，取当前节点和处理人。
2. 用该处理人账号登录、选租户、打开同一详情 URL；多角色时按前述登录态限制使用已保存的显式 loginId 或拆分批次，不在同一脚本写多个账号密码。
3. 填「审核意见」，点「同意」；发起人确认等节点按页面按钮点「确认」。
4. 等待返回列表或提示，读取行状态，进入下一节点。
5. 记录节点、处理人、账号、意见、时间、结果。

节点特例：

- **发起人上传定稿**：上传合同定稿，填意见，点同意。
- **合同管理员盖章**：按普通节点同意。
- **发起人确认**：通常需要上传合同扫描件再确认；若上传接口 200 但组件不登记文件、点确认无请求，按页面缺陷记录并请用户手动完成，不能伪造通过。

## 5. 终态断言

- 列表行状态为「已完结 / 已完成」。
- 详情审批流程所有节点都显示处理人、处理意见、同意/确认和时间。
- 合同编号已生成、附件在详情可见。
- 不用“流程走到最后”代替终态断言；必须有列表或详情状态证据。

## 6. 失败处理

| 触发 | 处理 |
| --- | --- |
| 登录 401 / 停在 `/login` | 从用户管理核对账号/状态/租户；不向用户索要密码 |
| 无「同意」按钮 | 账号不是当前处理人，或打开了 BusinessProcess 预览页；改用 OperationContractDetail |
| 点确认无请求、无提示 | 检查必填上传/意见；上传组件不登记文件按页面缺陷转人工 |
| 创建页审批人字段禁用 | 审批链由审批流配置解析，后端仍会生成；以详情页实际节点为准，并记录页面显示缺陷 |
| 待办中心为空但合同显示节点 | 直接按详情 URL 处理；待办任务生成异常单独记录 |

## 7. 输出

- 节点表：节点 / 处理人 / 账号 / 意见 / 时间 / 结果。
- 终态证据：列表状态、详情 URL、合同编号。
- 未覆盖项与页面缺陷，不把人工介入写成自动通过。
