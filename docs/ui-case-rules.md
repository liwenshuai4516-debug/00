# UI 用例粒度与规则维护

默认一条 case 验证一个独立业务目标和一种输入条件；业务目标相同的多个必要断言可以保留在一起。一个 Playwright test、一个页面或一次探索不天然等于一个独立业务目标。

## 拆分示例

| 合并的场景 | 应维护的独立用例 |
| --- | --- |
| 合同编号命中、无结果、重置 | 编号命中；编号无结果；带编号筛选后重置，各自独立准备初态 |
| 合同名称命中、无结果、重置 | 名称命中；名称无结果；带名称筛选后重置 |
| 表头、统计卡和发起入口都存在 | 列表表头结构；统计卡标签与单位；发起入口可达 |
| 上一页、下一页与查询后页码恢复 | 下一页；上一页；查询后的页码行为，分别准备所需页码和数据 |

无结果查询可同时断言总数为零、没有数据行、空态可见，这些共同证明一个目标，无需机械拆成三例。组合筛选验证条件交集也是一个目标。打开新建表单后检查必要字段和操作入口可以共同证明“表单可达”，不表示提交、必填校验已覆盖。用户明确要求端到端业务链时标为 E2E，单独维护，不替代各功能独立用例。

每例必须能单独运行、调换顺序运行；自行准备并核对身份、初态和数据。可以使用共用登录准备，但不能依赖另一例遗留的筛选、页码、浏览器上下文或业务数据。重置例先建立筛选属于前置准备，验证目标仍只有重置；清理不增加业务测试目标。

## 维护位置与生效范围

| 规则 | 维护入口 | 生效范围 |
| --- | --- | --- |
| 通用测试设计、独立性和覆盖要求 | 应用「设置 → 提示词」的默认业务提示词 | 保存后新对话；已有对话保留原提示词快照 |
| 被测项目专属规则、数据准备及业务口径 | 被测项目实际工作目录的 AGENTS.md，较长规则放在明确引用的文档 | 按 Pi 项目指引加载；在当前任务要求 Agent 读取最新规则 |
| UI 工具操作、探索与候选约束 | 客户端 resources/testing/ui/skills/qa-ui-basic/SKILL.md；断言检查在 qa-ui-assertion/SKILL.md | 客户端内置技能，属于应用维护；不在单次任务中修改它来迁就测试结果 |
| 本次页面范围、输入条件、预期及来源 | 当前任务的覆盖清单与各探索 contract | 当前测试任务；expected 在探索前冻结 |

内置默认提示词在 `src/main/prompts/test-agent-prompt.mjs`。修改源码不会覆盖使用者已经保存的默认提示词，也不会修改已有会话快照。已自定义提示词时，将需要的规则合并到设置中，再新建对话；当前对话要明确补充新规则，不能假定保存设置后已自动生效。

建议在默认业务提示词中维护以下规则：

> 一条用例只验证一个独立业务目标及一种输入条件。查询命中、查询无结果、重置和分页分别成例；允许多个断言证明同一目标。每例独立准备初态和数据，不依赖其他用例或执行顺序。生成前列出“检查项编号、功能、输入条件、预期来源、计划 caseId”的覆盖清单；已有设计稿逐项映射。交付按条目标记设计、候选、验证、发布、受阻或待确认，分别统计数量；不固定生成条数，不把部分完成写成整页完成。只有明确要求的端到端流程可以保留跨功能链，并标为 E2E。

## 与现有工具契约衔接

`qa_ui_save_candidate` 要求候选完整继承任务的 expected，并为每条 expected 提供业务断言，因此必须在探索前按目标拆任务。已经混合多个目标的任务不能靠删除候选预期来拆分，需要按各自目标取得真实探索证据。冻结版本保持不变；新规则不追溯改写已有资产。

覆盖清单决定数量，探索步数预算不决定 case 数量。设计稿、候选脚本、已验证版本和正式发布资产分别统计；探索失败的检查项保留为受阻，不算已生成，也不自动删去。发布门槛检查脚本结构与实际回放，不能自动证明业务粒度、规则来源或语义覆盖完整；这些仍须按上述规则核对。
